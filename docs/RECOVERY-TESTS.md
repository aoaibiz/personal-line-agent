# 障害・復旧試験（2026-10-24）

対象：GitHub main `acdd7bacacd60776f25a94ce51453aaa0bca933d` / 0.3.0候補、macOS上の既存実アカウント。常駐受信プロセスは既存0.2.2。秘密・本文・実アカウントのID・非公開の試験記録は掲載しない。

合格条件：利用者のPC操作なしに再開し、アカウント・履歴・権限・受信位置・送信台帳を保つこと。正常な実接続を確認してから障害を注入した。復旧はコード・プロセスの範囲に限定し、認証情報やDBを過去のコピーに戻さない。重大・高の例外判断は所有者のみ。

| 試験 | 実施内容 | 観測結果 |
| --- | --- | --- |
| 正常経路 | 実LINEのプロフィールと保存済みMIDを照合 | 実通信成功、DB整合性正常 |
| プロセス単位の通信断 | 診断プロセスだけ接続不可のローカルHTTPSプロキシへ向け、実際に通信を失敗させる | `line_transport_failed`を検出。設定を外した次の実通信は成功。Mac全体のWi-Fi断ではない |
| 受信プロセスの停止 | 実常駐受信プロセスへSIGTERM、終了後10秒観測 | 自動再起動なし。エージェントが再起動してlisteningへ復旧。無人の自動復旧としては不合格 |
| 保存データの維持 | 上記試験前後を比較 | DBのinode・連絡先件数・整合性・権限情報のハッシュ・結果不明の操作一覧は不変。保存メッセージ数の減少なし |
| 壊れた更新 | 構文が壊れたpyprojectを試験用候補に用意し、実uvインストールを実行 | `release_install_failed`で拒否。稼働版の選択情報は変更なし |
| 再認証の入口 | 標準入力がターミナルではない状態で実CLI loginを起動 | `interactive_terminal_required`で認証開始前に拒否。QR/PIN表示なし。既存認証は失効させていない。スマホだけの再認証経路としては不合格 |
| GitHubからの新規導入 | 公開リポジトリを別フォルダへclone、固定lockで非editableの新venvへ導入 | 0.3.0起動と実通信成功。同じOS利用者・既存アカウント認証を再利用しており、新しい利用者の初回本人確認を検証したものではない |

## 判明した問題

| 区分 | 起きる条件・外部から届く経路 | 影響 |
| --- | --- | --- |
| 高 | 常駐受信プロセスが終了する。外部入力だけによる再現は未確認で、試験は管理側からの停止 | 配布版に受信の自動再起動機構がなく、今回の観測期間内に自動では受信を再開しなかった |
| 高 | LINE再認証が必要になる。LINE側で失効させた実試験は未実施だが、現再認証入口は非対話実行を拒否する | スマホだけで復旧する製品要件を満たさない |

この結果を「全運用完成」と扱わない。受信プロセスの監督・再起動と、正式に対応する所有者専用のスマホ認証画面が必要。

## 未実施の条件

- Mac全体の再起動、電源断、OSログイン前からの再開。受信の起動監督がないことが先に判明したため、作業中のMac全体を再起動して合格を装わない。
- LINE側の実際の強制失効、新しいOS利用者、別のスマホホスト、Windows。
- 停止中のメッセージ回収：別途120.34秒の停止区間を設け、受信側へ試験送信を依頼した。再開後60秒までに対象アカウントの新規受信記録を確認できず、照合するメッセージがないため未確認。復旧後の受信状態はlistening。未確認を受信漏れ／回収成功のどちらにも断定しない。
